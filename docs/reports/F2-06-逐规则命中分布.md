**同一个成因裂成了 8 行**，每行 1~8 个文件。看表的人会以为那是 8 种不同的原因，它其实是同一句话的 8 个数字。

原因在 `ingest/report.py` 的分组键：`bucket()` 对「规则之外」的理由取**前 28 个字符**（`OTHER_PREFIX`）当归并键——这个设计是为**路径**留的（错误消息里带路径，原样分组会得到几百个各含 1 条的分组）。而 `max_file_mb` 超限那条理由第一版把**逐文件不同的大小**写进了这 28 个字符之内：

```python
f"超过 [scan] max_file_mb = {limit}（{size:.1f} MiB）：只记名字与元数据"
#                          ^^^^^^^^^^^^^^ 第 24 个字符起就是变量
```

第二个缺陷在同一行里：`[scan]` 是配置节的名字，**rich 把方括号当样式标记连词一起吃掉**，终端上印成 `超过  max_file_mb = 64`（多一个空格、少一个词，不报错）。这是本项目**第三次**撞上方括号（前两次是 `--root` 的帮助文本、目录名里带方括号的路径）。

**修法（`33b16fb`）**：

1. 改的是理由的**语序**，不是放宽 `OTHER_PREFIX`——阈值在一次运行里是常量，留在前缀里；大小压到最后。修后同一栏只剩**一行**：`超过 [scan] max_file_mb = 64：只…`，**29 个文件 / 12,352.0 MiB**；
2. `cli/commands/index.py` 里凡是从数据来的文本（扫描根、规则文件、归属、理由、例、错误消息、零命中规则的原文）**一律过 `rich.markup.escape()`**；静态文案不过（那几个 `[bold]` 是代码里自己写的）。

两条各配一条测试（`tests/unit/test_cli_index_dryrun.py`），且**都先在旧版本上确认过会红**：同成因必须落在同一行的端到端断言（失败信息里直接能看到 `（1.` 与 `（2.` 两行）、路径与 glob 里的方括号必须在报表里活着。`ingest/scanner_scandir.py` 是被测模块，按「绿灯不自动续期」，`F2-01` 与 `F2-05` 随这次提交重跑（记录见 [PROGRESS](../PROGRESS.md) §4 P2）。

> **放宽 `OTHER_PREFIX` 治不了这个病**，这一点写进了 `report.py` 的注释：理由是**给人读的消息**，拿它当机器用的归并键本身就脆——下一次谁把数字写在前面，症状还是"报表看起来是好的，只是多几行"。正解是让扫描器给一个**机器可读的成因**，见 §4 与 PROGRESS 的遗留。
