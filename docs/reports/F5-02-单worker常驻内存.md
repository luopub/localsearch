# F5-02 单 worker 常驻内存：原始输出

* **功能点**：`F5-02`（多进程调度，验收项 `A2`）
* **工具**：`tools/measure_worker_rss.py`——走**产品路径**（`EmbedPool` + `iter_requests`），
  不另写一份推理
* **读数去处**：`PROGRESS.md` §3 的 `E41`；`PER_WORKER_RSS_BYTES` 这个常数取自这里
* **为什么单独一份报告**：这条读数**不可重复**——
  1. 峰值常驻内存取决于**起手时有多少可用内存**（P0「与计划的偏差」第 11 条：内存池按可用内存
     生长），而这台机器上的可用内存在 3–8 GiB 之间波动（`E7`）；
  2. **一个进程只能量一档**（峰值只增不减），所以"两档"必然是两个进程、两次运行。
* **机器**：15.37 GiB 物理内存 / 8 物理核 16 逻辑核（`E6`/`E7`）；
  配置 `onnx int8 dim=768 batch_size=8 max_seq=2048 threads=8`。

---

## 1. 命令

两条命令**逐字**如下，每条各自起一个进程（**不要**在同一个进程里连跑两档）：

```bash
# 短切片那一档（typical）
HF_HUB_OFFLINE=1 PYTHONUTF8=1 uv run python tools/measure_worker_rss.py --tokens 512 --count 24

# 长文本那一档（worst）
HF_HUB_OFFLINE=1 PYTHONUTF8=1 uv run python tools/measure_worker_rss.py --tokens 2048 --count 24
```

`--count 24` = 3 个批（`batch_size = 8`）。语料是**合成的**（不读盘、不依赖任何数据目录）。

## 4. 这些数说明什么

1. **`max_seq = 2048` 的代价第一次有了数**：峰值 1.81 → 7.17 GiB（约 **4 倍**），
   暖吞吐 562 → 272 与 490 → 330 tok/s（**1.5–2.1 倍**，两轮各给一头；这个口径下两次读数
   本身就差十几个百分点，见 §6）。原来 2048 是拍的（`F5-01` 的遗留）。
   ⚠ 这一轮**不改它**：切片长度与 `max_seq` 一起归 `F5-04`。
2. **`A2` 在本机算不出 2**：可用 3–5 GiB − 保留 2 GiB，除以 7.17 GiB 得 **1**（还是靠
   `MIN_WORKERS` 兜住的）。所以本机跑的**就是**那条"就地跑"的路径，"W 恒为 1"不是一个注释。
3. **短切片档与 `E8` 对得上**：`E8` 的 2.01 GiB 与本轮的 1.81 GiB 是同一个口径、同一个量级
   （差 10%），而且本轮两次独立运行**逐字节相同**——这个档位的读数是稳的。
4. **长文本档不稳**：7.17 与 6.89 GiB 两次不同，差值 4%，而起手可用内存从 3.54 涨到
   4.67 GiB。这与"内存池按可用内存生长"的形状一致，也是**取大的那个**的理由。
5. **峰值可以超过当时可用的内存**（第一轮长文本档：起手 3.54 GiB 可用、峰值 7.17 GiB）。
   所以这个数**不是**"这个配置至少要多少"，而是"它在这台机器上长到了多少"。

### 4.1 口径：实际 token 数与目标差了 20%

`build_corpus()` 是**按字数**拼的近似（中文一字约 0.74 token）：

* `--tokens 512` → 实际 **416 token/条**（差 −19%）
* `--tokens 2048` → 实际 **1622 token/条**（差 −21%）

后果有两层，都要写在明面上：

* **进 `PER_WORKER_RSS_BYTES` 的那个数对应的是 1622 token 的批，不是 2048 的批。**
  所以它对"一条占满 `max_seq` 的切片"来说是**下界**。偏小的方向正是危险方向（先验偏小 →
  `W` 偏大），所以这条进 §4 P5 的「遗留」，等 `F5-04` 定下切片长度时连同 `max_seq` 一起重量。
* **为什么没把它凑准**：凑准要先知道 tokenizer，而先建一份嵌入器再量峰值，会让"两份模型"
  混进同一个进程的读数（这个工具的设计原则是**一个进程只建一个嵌入器**）。这一轮选了
  "如实报实际 token 数"而不是"凑准目标数"，并把这条写进了工具的输出（§5 的第 2 条改动）。

## 5. 两轮之间改了什么（不是同一版二进制，所以要说清）

改动**只在打印与常量上**，测量路径（语料、两趟结构、`EmbedPool` 那一趟）一个字没动：

1. `PER_WORKER_RSS_BYTES`：第一轮还是占位的 `3.4e9`，第二轮已是本轮实测的 `7.7e9`。
   两次算出来的 `W` 都是 **1**、走的都是同一条就地路径，所以**峰值读数可比**。
   （第二轮打印的"单 worker 先验值 7.17 GiB"就是第一轮长文本档的读数——先读到、再写进代码、
   再复跑一次。峰值与这个先验值无关，所以不构成循环论证。）
2. 打印口径修了两处：
   * "冷 − 暖 = 加载时间"这个估计，在**暖比冷慢**时会打印出一个**负数**（第一轮长文本档打的
     是"含加载 −16.92 s"）。现在分两支：冷 > 暖 时印估计值并说明它把两趟之间任何差异都
     算成加载；暖 > 冷 时直接说**分不出加载**、并提示 tok/s 一起存疑。
   * 峰值同时印**字节数**（`1.81 GiB = 1938706432 字节`）：`PER_WORKER_RSS_BYTES` 要的是
     字节，两位小数的 GiB 反推不回原值（7.17 GiB 那一趟就是这么丢了精度的）。
3. 实际 token 数与目标差 > 10% 时**出警告**，并给出把 `--tokens` 调到多少能凑准（§4.1）。

## 6. 这些数**不**说明什么

* **不是 `A2` 的性能那一半。** `A2` 要的是"`W ≥ 2` 时整机有效吞吐 ≥ 0.9 × `W` × 单进程"，
  而本机 `W` 恒为 1——那个倍数**这一轮没量、也量不了**（归 `F7-04`）。本轮的产出是**机制**
  与这一个输入常数。
* **不是"这台机器上单进程最慢/最快多少"**：同一配置两轮之间 tok/s 差 13%（短切片档）与 21%
  （长文本档），而且**差距的方向与可用内存不一致**（内存多的那轮短切片档反而更慢）。所以这个
  口径下的两次读数差十几个百分点是正常的，别拿它做 1% 精度的比较。
* **不是稳定复现的加载耗时**：短切片档估出加载 2.45 / 4.75 s，与 `E40` 的 ONNX
  2.30–3.56 s 同量级、与 `M5` 的 0.50 s 仍然对不上（`F5-01` 那条偏差**还在**，本轮没归因）。
* **不是"再多的批会不会继续涨"**：每个进程只跑了 3 个批（24 条 / 批 8）。ONNX 的内存池
  在更多批下会不会继续长，这一轮**没量**。
* **不是"别的机器/别的配置也这样"**：换机器、换 `batch_size`、换 `max_seq`、换后端都会让这个
  数变。所以它进代码时带的是"**先验**"三个字，并且每个 worker 会自报实测峰值
  （`BatchResult.peak_bytes`）。
