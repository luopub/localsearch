# 2. 分析

## 2.1 本轮结掉的三条功能点

| 功能点 | 问题 | 结论 |
|---|---|---|
| `F0-01` | bench 工具能不能测出可信数字 | **能**。24 个「批 × 线程」档位 + dtype 对比 + 跨后端一致性 + 并行探测全部跑完，两次进程退出码均为 0，无 `[FAIL]` |
| `F0-02` | ST 与 ONNX int8 选哪个（**D9**） | **选 ONNX int8**。同一轮内 553.0 vs ST float32 的 482.0 tok/s（**+14.7%**）；冷启动 **0.50 s vs 5.89 s（快 11.8 倍）** |
| `F0-03` | 本机到底多快（**M4**） | 有效吞吐 **553.0 tok/s**（ONNX int8，8 线程，批=8）→ 15 亿 token 约 **754 小时 ≈ 31 天**（单进程，未计去重收益） |

## 2.2 两轮实测并排看（**这一段是本报告最该看的部分**）

同样的脚本、同样的语料、同样的机器，跑了两轮，数字**不可互换**：

| 项 | 第 1 轮 `b6e001c` | 第 2 轮 `5c488fe`（本轮） |

| 运行时刻 | 2026-10-14 11:20:10 | 14:26:08 / 14:46:15 |

**两轮在哪里一致（所以可以当结论）**：ONNX int8 都比 ST float32 快；余弦一致 0.9999；ST 冷启动都是 5.89 s；最快档位都是 `线程=8 批=8`（ONNX 侧）。

**两轮在哪里不一致（所以不能当常数）**：稳态吞吐差 **12%**（619.2 / 553.0），dtype 比差 **2.5%**（6.06 / 6.21）。**这不是脚本的问题，是机器的**——本机同时跑着浏览器与编辑器，占用率在 48%–73% 之间浮动，多线程档位吃满核心，被别的进程一挤就掉。更早几轮里同一个 `ST 线程=8 批=8` 档位量到过 **337.3** 与 **514.2** tok/s，**差 52%**。

> **由此定一条用法**：这类数字**必须连"当时的内存占用率"一起记**，否则两次测量不可比。本报告和 `PROGRESS.md` §3 都照此记。计划 §3.2 那种"给一个数就往下推"的写法在这种机器上不成立。
>
> **`M4` 取哪个值**：取本轮（`5c488fe`）的 **553.0**，因为测试记录的「代码版本」栏要对应一个提交，而 `5c488fe` 是当前提交。第 1 轮的 619.2 保留在表里，**当作同一配置的上限**。计划 §3.2 的推算用保守侧 553.0 → 31 天。

## 2.3 最该记住的发现：**dtype 的失败方式是静默的**

模型的 `config.json` 声明 `"dtype": "bfloat16"`。**不显式传 `dtype` 就直接构造 `SentenceTransformer`，它会照 config 用 bf16 加载。** 而本机 CPU 是 **Zen 2（Ryzen 7 4800H），没有 bf16 硬件**，torch 只能软模拟：

- 实测 **71.4 tok/s**（第 2 轮）/ 94.2 tok/s（第 1 轮），而 float32 是 442.9 / 527.2 → **慢 6.2 倍**
- **它不报错、不警告，只是慢。**

这类问题最坏的地方是**归因**：它会一路带到 P5，以"怎么这么慢"的形式暴露，而那时已经铺了几百行代码在上面，很难想到根因是一行默认参数。所以 `PROGRESS.md` §3 的 `M2` 行补测了这条，并写明 **`[embed] dtype` 必须显式写 `float32`**。

**顺带量到一个次要现象**：bf16 下向量范数是 **1.0017** 而不是 1.0，即归一化只有约 3 位有效数字，会让余弦读数 >1。不影响结论（bf16 已被速度一票否决），但记下来。

**仍未测**：计划 `M2` 说的"**fp16 产出 NaN**"这一半，本轮**没有验证**——bench 只跑 fp32/bf16 两档。别把"bf16 慢"读成"fp16 会 NaN 已验证"。

## 2.4 内存是本机的硬约束，而且它反直觉

本机总量 **15.37 GiB**，其中约 9 GiB 常被浏览器与编辑器占着。脚本要依次加载**三份**模型：ST fp32、ST bf16（dtype 探针）、ONNX int8。默认它们全部常驻。

**在本轮修好之前，连着两轮段错误退出**：

| 轮 | 提交 | 开始时空闲 | 峰值 RSS | 结局 |
|---|---|---|---|---|
| bench2 | `69bad20` | — | 7.49 GiB | `EXIT=139`（SIGSEGV） |
| bench3 | `b6e001c` | 6.23 GiB（占用 59%） | 6.89 GiB | **`EXIT=0` 跑完** |
| bench4 | `99f3a8c` | **7.84 GiB**（占用 **48%**） | **8.06 GiB** | `EXIT=139`（SIGSEGV） |
| bench5 | `5c488fe` | 5.64 / 6.77 GiB | 6.11 GiB（ONNX 进程） | **两次进程都 `EXIT=0`** |

**注意 bench3 与 bench4 这两行**：同一份释放逻辑，**唯一显著差别是开始时可用内存（6.23 vs 7.84 GiB），而崩掉的那一轮可用内存更多**。这与"torch 与 onnxruntime 的内存池**按可用内存生长**"一致——可用得越多，它抓得越多，墙只是往后挪。

> **所以"先把别的程序关掉再跑"对本进程无效**：腾出来的空间会被它一并吃掉。这条反直觉，但两轮实测一致。
>
> 需要说明的是，**这个解释没有被完全隔离验证**（两轮之间还夹着 `99f3a8c` 那个 dtype 探针的改动），列在这里是因为它与"拆进程之后就不再崩"这个结果方向一致。**真正解决问题的是拆进程**，不是省内存。

**修法是让三份模型别挤在一个进程里**（`5c488fe`）：拆成两次进程，各自跑完就退出；而第 5 步的跨后端一致性核对需要两边都在，于是第一次把 ST 侧向量存成 `.npz`，第二次读回来比对（`--save-emb` / `--load-emb`）。**这个检查是速度对比成立的前提，不能为了省内存丢掉。**

**另一条内存事实**：ONNX 的**批大小是内存的主要杠杆**。批=8 那一整块跑完，进程峰值才 **2.66 GiB**；批=16 跳到 **4.88**；批=32 到 **6.11**。

> 读这三个数要注意脚本自己的提醒：**末列 RSS 是进程峰值，只增不减**，所以它不是"这一档的独占占用"，而是"跑完这一档为止的上界"。因为这个方向是单调的，**每一块之间的台阶是真实的**——批=8 就地跑完只需 2.66 GiB，而批=16/32 至少各要 4.88 / 6.11 GiB。
>
> **一个幸运的巧合**：ONNX 侧**最快的档位恰好也是最省内存的**（线程=8 批=8，553.0 tok/s）。并行设计正好可以用它。

## 2.5 `A2`（整机并行 ≥ 单进程 8 倍）在本机算术上不可达

**这不是"还没测出来"，是"放不下"，调参解决不了。**

- 单 worker 峰值常驻内存实测 **2.01 GiB**（第 1 轮并行段，ONNX int8，批=8）
- 8 个 worker → **16.09 GiB**，而整机总物理内存只有 **15.37 GiB** → **105%**
- 且本机是 **8 物理核 / 16 逻辑核**（SMT 2.0×），8 个 worker 还要互相抢核心

**根源在计划 §3.1**：它把 CPU 记成"AMD64 16 核"（把逻辑核当成了物理核），于是 §3.2 的 `workers = min(8, cores // 2)` 给出 **8**——按物理核该式给出的是 **4**。同时计划假定"torch 每进程约 1–1.5 GB 常驻"，实测 **2.01 GiB**，**偏低约 40%**。

**本轮只量到 1 个 worker（第 1 轮：598.5 tok/s，加速 0.97×）**。0.97× ≈ 1.0 是**正确的**——1 个 worker 本来就拿不到并行收益；它的价值在于证明**测量方法没问题**（更早一版量出 0.45×，那是父进程占着模型去判断内存，错在方法，已修）。`workers=2/4/8` 因内存判据**全部跳过**。

**没有量到的部分，用"算"补不回来**：本机拿不到 `workers=2/4/8` 的数字，就**无法用实测反驳**"并行到底能加速几倍"。但 8 worker 那条**不需要测**——它首先就放不下。**所以 `A2` 记为未通过，且判据本身要用户重定。**

> 并行段是本工具**唯一会同时按下多份模型**的地方，实测它**两次把本机拖到无响应/段错误**。所以判据（放行后须给系统留 `max(4 GiB, 物理内存 25%)`）取的是保守值，**默认宁可跳过**。要拿这些数只有两条路：换一台内存更大的机器，或降低单 worker 占用——**批=8 已是最小受测档，再小的 batch 是否更省，没测过，别当已知。**

## 2.6 与计划 §3.2 的对照

计划原本估"首次全盘索引 100–400 小时"，依据是[anygrep](https://github.com/kuroko1t/anygrep) 作者在 **Ryzen 7 7700** 上实测的 ~1100 tokens/s——**别人的机器、口径未必一致、也未确认是否批量**。

**实测作废了那两行，而且两端都错了方向**：本机 553.0–619.2 tok/s，**比原"悲观"值 1100 还低**。原因与本计划原先的猜测一致但更强：本机是 Zen 2，**没有 VNNI 指令集**，int8 收益远不如 Zen 4。

**而且原来指望的"靠 8 路并行对冲"已经失效**——见 2.5，本机跑不起来。所以：

> **单进程约 28–31 天，且没有靠并行缩短的余地。** 唯一仍然有效的杠杆是**砍语料**（严格排除规则、内容去重）：每砍掉一份语料就是线性砍掉索引时间。

## 2.7 本轮修掉的三个"测量方法的错"

都记下来，因为它们的共同点是**不报错、只给一个错结论**——比崩溃更坏，崩溃至少会让人停下来看。

1. **拿父进程的脚印量子进程**（`69bad20`）：并行段要用"单个 worker 占多少内存"来判断还能放几个，而父进程自己占着约 2 GiB 模型没放。第一版因此把 `workers=1` 量成 **0.45×**——同等工作理应 ≈1.0。
2. **三份模型同时在手**（`b6e001c`）：段落边界加 `release_models()`。注意**峰值 RSS 只增不减**，所以"释放了"光看峰值看不出来，要看下一档位还涨不涨、或可用内存是否回升。
3. **dtype 对比取自错误的运行对象**（`99f3a8c`）：比值应当用 **dtype 探针自己刚跑的那两条**，而第一版的取值逻辑却在全部 `runs` 里回搜 `dtype == "float32"`，命中了主扫描里另一个档位，于是打出 **6.06×** 而探针自己的两条是 **5.60×**。这类错**看不出错**——数字合理、方向也对，只是不是同一对。

> 第 3 条是**报告写完、回头核对时才发现的**：当时注意到"探针刚跑的两条是 527.2 和 94.2，比值该是 5.60 而不是脚本打印的 6.06"。
