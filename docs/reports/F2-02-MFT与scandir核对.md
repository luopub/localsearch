## 一、先看这几条

1. **除了两条，两侧一条不差。** 路径相同的 **1,025,639** 条，`仅有 MFT 0`、`处置不一致 0`、`文件/目录判断不一致 0`；目录数两侧**逐位相同**（47,754），`仅名字 744,560`、`排除 1,464`、`剪掉 1,588` 三栏也逐位相同，正文字节数都是 **22.91 GiB**。差异只有文件数（MFT 980,937 / `scandir` 980,939）与那两条"仅有 scandir"。

2. **那 2 条不是"两个后端对文件系统判断不一致"，是同一种东西被两种取属性的方式看到了不同的东西**：`D:/work/test/opencode/nul` 与 `D:/work/test/opencode-skilltest/nul`，**文件名是 Windows 的保留设备名**。`scandir` 从目录枚举里得到它（真文件，属性 `0x20`，83 / 0 字节）；MFT 后端要**逐条打开路径问属性**，Win32 把 `…\nul` 解析成 `\\.\NUL` **设备**，`GetFileAttributesExW` 报 87（ERROR_INVALID_PARAMETER）。于是这两条在 MFT 的记录流里**根本不存在** → 记进"读不到的 2 条" → 核对时成了"仅有 scandir 且 FRN 对不上"。定性过程与原始读数见**第三节**。

3. **判定仍然是不通过**，而且这次是判据在正确工作：差异占比 2 / 1,025,639（**0.0002%**），它没有放过；`frn_of` 对这两条返回的是 `os.stat` 给的 **0**，也没有被当成"折叠成功"（`ScanEntry.frn == 0` 的语义是"不知道"，按无法解释计）。

4. **MFT 比 `scandir` 慢 3.14×**：205.89 s 对 65.52 s，而**枚举本身只占 43.49 s**。这推翻了"全盘枚举更快、所以 MFT 当快路径"的直觉，拆解见**第四节**。⚠ `scanner_mft.py` 的模块文档本来就写着"本模块不承诺 MFT 的冷扫比 scandir 快……真正的读数由真机核对那一轮给出"——**现在读数有了，它站在 scandir 那边。**

5. **账目闭合**（这一轮最值钱的副产品：整卷记录与账目之间没有悬空）：

   | 侧 | 恒等式 | 验算 |
   |---|---|---|
   | MFT | 整卷记录 = 根自身 1 + 不在根下 + 系统保留 + 被剪枝 + 条目 + 读不到属性 | `1 + 1,200,599 + 0 + 1,634,010 + 1,028,691 + 2 = 3,863,303` ✓ |
   | `scandir` | 条目 = 进核对 + 剪掉的目录 + 排除 | `1,025,641 + 1,588 + 1,464 = 1,028,693` ✓ |

   上一次`F2-06`的 `--dry-run` 账目里，`剪掉的目录 + 排除` 与条目数的差也是这么合上的。

6. **与 4 小时前那个 `F2-06` 读数比**（03:52 的 `1,028,685`）：文件数 **+8**（`scandir` 口径），正文仍是 22.91 GiB，`排除` 1,465 → 1,464。**`D:/work` 是活的**（本仓库自己就在里面），两次试跑的计数不该逐位相等。

## 三、那两条差异的定性（同一台机器上的验证，非推理）

对两条路径各做了四件事：`scandir` 的条目、`os.stat`（原样）、`GetFileAttributesExW`（原样）、以及**加 `\\?\` 扩展前缀**之后同样的两件事，最后试着读出内容。结果（`D:/work/test/opencode/nul`，83 字节那个）：

| 查法 | 结果 |
|---|---|
| `scandir` 的条目 | 真文件：`is_dir=False`、属性 `0x00000020`、**大小 83**、条目上的 `st_ino=0`（`F0-04` 已知的陷阱） |
| `os.stat(原样)` | **成功**，但报 `st_ino=0 / 大小=0 / 属性=0x00000000` —— 那是 **NUL 设备**，不是那个文件 |
| `GetFileAttributesExW(原样)` | **失败，`GetLastError=87`（ERROR_INVALID_PARAMETER）** ← 报告里那两行的来源 |
| `os.stat(\\?\)` | 成功，`st_ino=9007199255558856`（记录号 817,864 / 序号 32）、大小 83、属性 `0x20` —— **真文件** |
| `GetFileAttributesExW(\\?\)` | 成功，属性 `0x20` |
| `open(原样)` 读 16 字节 | 返回 **0 字节**（NUL 设备读到 EOF），**不是**那个文件的内容 |
| `open(\\?\)` 读 16 字节 | `b'dir: cannot acce'` —— 文件里真装着的文本 |

另一条 `D:/work/test/opencode-skilltest/nul` 同形，只是它是 0 字节：真 FRN `281474979948991`（记录号 3,238,335 / 序号 1）。

**结论**：`nul` 在 Win32 的路径解析里是保留设备名，`…\nul` 被解析成 `\\.\NUL`。**只有 `\\?\` 前缀（把路径直接交给内核、跳过 Win32 的名字解析）能拿到真文件。** 两个后端看到的是同一个文件，差别在取属性与读内容的方式：

- `scandir` 的属性**来自目录枚举**（`FindFirstFileW` 那一路），从不打开路径 → 看得见；
- MFT 后端的属性**靠 `GetFileAttributesExW(path)`**，要 Win32 解析整条路径 → 看不见。

**这不只是核对的事，是一个真的产品缺陷**：这一类名字（`nul` / `con` / `aux` / `prn` / `com1`-`com9` / `lpt1`-`lpt9`，**带扩展名也算**，如 `nul.txt`）在 MFT 后端下会**整条消失**；而在 `scandir` 后端下会进索引，等到 `F3` 打开它提取正文时——`open()` **会成功**，读到的是**设备的 0 字节**，于是这个文件**静默地索引成空**。这正是本项目明令禁止的"静默返回不完整结果"。修的地方是同一个：路径的可达性（`\\?\`），属性读取与内容读取各用一次。

⚠ 一条**没有被本轮行使**的风险（推理，不是观察到的）：如果设备对 `os.stat` 返回的 `st_ino` 恰好等于某个真实存在的 FRN，核对就会把它折成"硬链接"而**静默通过**。这一次设备给的是 **0**，被 `frn == 0 → 无法解释` 那条挡住，所以没有发生。

**修法尚未开工**，见第五节。

## 四、耗时拆解：那 3.14× 差在哪（微基准，不是整轮）

`scanner_mft.py` 的模块文档给的前提是"补属性 `os.stat` 36 µs/条、`GetFileAttributesExW` 14 µs/条（`F0-04` 对拍），改用后者才勉强划算"。整轮实测是 **157.9 µs/条**（`(205.89 − 43.49) s / 1,028,691`），所以逐项量了一遍。

**第一版量错了，记在这里**：把 `attributes_of` 量在 `os.stat` 前面，得到 **62.5 µs 对 5.8 µs**——同一批路径、同类调用差十倍。那不对称更像是**测量顺序**（先量的那个吃掉冷启动与首次访问）而不是 API 本身。改成 A/B 交替、每轮内部换先后、7 轮取中位数之后：

| 组件 | 中位数 | 折到整轮 |
|---|---|---|
| `ntfs.attributes_of` | **5.3 µs/条**（各轮 5 5 5 5 5 6 5） | 1,028,691 × 5.3 µs ≈ **5.5 s** |
| `os.stat(follow_symlinks=False)`（对拍） | **5.7 µs/条** | — |
| `base.normalize` | 2.2 µs/条 | ≈ 2.3 s |
| `rules.decide`（284 条规则全表） | 11.0 µs/条 | ≈ 11.3 s |
| `ScanEntry` 构造（含 `decide` 与 `rsplit`） | 22.9 µs/条 | ≈ 23.6 s |
| 字符串拼接 `parent + "/" + name` | 0.4 µs/条 | ≈ 0.4 s |

（2,000 条真路径、平均 82.4 字符、来自 `D:/work/test/localsearch`。n=2000 只够看量级。）

**能读出来的三条**：

1. **属性调用不是瓶颈。** 5.3 µs/条，整轮约 5.5 s——即使全砍掉也救不回那 140 s。⚠ **文档里"`os.stat` 36 µs / `GetFileAttributesExW` 14 µs"这组对拍数今天不成立**：两者几乎相等（5.3 对 5.7，比值 0.93×）。**原因未查**（样本、卷、冷热、杀软都可能），但**"改用 `GetFileAttributesExW` 才划算"这个理由现在没有实测支撑**。另一个理由没变：它不开句柄、不触发杀软的开句柄回调（`ntfs.attributes_of` 的文档）。
2. **微基准能解释的约 40 µs/条（≈41 s），实测整轮 157.9 µs/条——剩下约 120 s 未拆分。** 头号嫌疑是 `_run_root` 里对**整卷 3,863,303 个槽**做的那一次 `_locate` 遍历（纯 Python 上溯 + 路径压缩），但这是**嫌疑，不是实测**。要证实或证伪只有一条路：在 `_run_root` 里给"枚举后逐槽定位""按深度序判定""收尾"各加一次 `perf_counter` 并印进报告（未做，见第五节）。
3. **结构性解释（推理，但机制清楚）**：MFT 按**卷记录数**付费（3.86 M，其中 2.83 M 与这个根无关，仍要逐槽定位它的父链），`scandir` 按**访问到的条目数**付费（1.03 M），它在"不在根下"和"被剪枝"那 2.83 M 条上**一分钱都不花**。`D:/work` 只占整卷的 27%，于是 MFT 为"看得见整卷"付了约 3.7 倍的单价成本。**这也解释了为什么 MFT 的赢面要整卷扫才可能出现**——而"整卷"恰恰是 MFT 最花钱的场景，除非它的记录数优势被摊薄（`F6-01` 的 USN 增量才是真正改代价曲线的那件事，`F2-02` 只是它的地基）。

## 五、这一轮没做 / 下一步

1. **`nul` 那一类没修。** 建议在 `ntfs.attributes_of`（属性）与将来的正文读取（`F3`）上**共用同一个"把路径变成可达"的转换**（`\\?\` 前缀；UNC 要写成 `\\?\UNC\server\share`；它要求绝对路径与反斜杠，且会**关掉** `.`/`..` 与正斜杠的归一化——所以必须只在一个地方做、且不许重复加前缀）。**未开工**：这动的是路径语义，属于跨功能点的改动，等指令。
2. **`_locate` 的分段计时没做**（第四节第 2 条）。这是把"约 120 s 未拆分"变成结论的唯一办法。
3. **硬链接那一半判据在真机上没有被行使**：`D:/work` 这棵树里硬链接 0 条，`仅有 scandir 2` 也全被判成"无法解释"而不是"硬链接"。折叠逻辑**只在单测里被行使过**（`test_scanner_parity.py` 用真 `os.link` 造的那条）。想让它真跑一次，得换一个真有硬链接的根（`C:/Windows` 的 WinSxS 里遍地都是）——**下一次核对换根时带上**。
4. **`F2-02` 的结论暂时只能是"不通过"**：判据本身没有问题，卡住它的是被验收的那两个后端之一。修完第 1 条要**重跑一轮**，报告另存一份（本节这一份留作对照，不覆盖）。
