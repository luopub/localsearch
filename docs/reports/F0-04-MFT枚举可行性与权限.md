# F0-04 MFT 枚举可行性与权限验证

**这是 P0 的最后一条功能点。** 它结掉的是计划里**唯一一条需要管理员权限**的验证，也是 `D11`（可替换扫描后端）与 `M8`（~200 万文件/分钟）的唯一实测来源。

- **类型**：**脚本化实测**（非单测）。MFT 枚举要提权、要在真实卷上跑，写不成单元测试，故按计划 §10.4 走"脚本入库 + 参数化命令 + 原始输出落盘 `docs/reports/`"这条路。
- **功能点 ID**：`F0-04`
- **代码版本**：`80760d3` 干净（`git rev-parse --short HEAD`；工作区无改动，三份日志各自的 `代码版本` 行都是这一行）
- **关联验收项**：**A1**（2 万文件基准集全量索引无未捕获异常——MFT 是 A1 的扫描后端之一）
- **落点**：`tools/probe_mft.py`（822 行，纯 `ctypes`，**不引入新依赖**）

## 这份报告怎么跑出来的

三条命令。**① 是正面证据、② 是负面对照、③ 是同卷对照基线**——三者合起来才够回答"能不能用、需不需要提权、比 scandir 快多少"：

```powershell
# ① 正面证据（管理员终端）
.venv\Scripts\python.exe -X utf8 -u tools/probe_mft.py --volumes "C,D" --rounds 2 \
    --log "%TEMP%\lsearch-probe-mft.log"

# ② 负面对照（普通终端）—— 证明"不提权就真的拿不到"，而不是"探针写错了"
.venv\Scripts\python.exe -X utf8 tools/probe_mft.py --volumes "C,D" \
    --log "%TEMP%\lsearch-probe-mft-noelev.log"

# ③ 同卷对照基线（普通终端）—— 与 MFT 比同一块盘的耗时的唯一办法
.venv\Scripts\python.exe -X utf8 -u tools/probe_mft.py --volumes "C" --backend scandir \
    --scandir C: --log "%TEMP%\lsearch-probe-mft-scandir.log"
```

退出码依次为 **0 / 2 / 0**。

> **为什么负面对照要单独跑一遍**：`F0-04` 的一句结论是"MFT 需要管理员"。**光有成功的运行证明不了这一句**——它只证明"提权时能用"。所以另跑一次不提权的，把 `ERROR_ACCESS_DENIED` 如实记下来。退出码 2 是**设计好的**，不是失败（脚本里写明"要跑 MFT 但没提权，本次不能作为 F0-04 的证据"）。

> **`--volumes` 这次显式写了 `C,D`**。探针的默认值是"所有已挂载卷"，而本机 `E:` 在 `GetDriveTypeW` 下报 `DRIVE_FIXED(3)` 却并不是本地盘（用户 2026-10-14 明确指示），**默认值会把它一起卷进来**。这条见下方「分析」第五节。

> **三份日志都是纯 LF、无 `\r`**（实测 `CR=0`），所以**没有做任何机械处理**，逐字节即原文。这一点与 [P0-模型预下载.md](P0-模型预下载.md) 那份不同（那份混着 tqdm 覆盖帧，需要处理并在文件头声明）。

# 2. 分析

原始输出里看不出来的事，写在这里。

## 2.1 M8：达成，余量 2.66×–4.23×

探针 §5 打的那个比值（`6.66×`）**偏乐观，它自己也知道并已标注**：分子是「**记录**/分钟」，分母的目标是「**文件**/分钟」，而 MFT 记录里含着目录与 NTFS 元数据文件（`$MFT`、`$RmMetadata` 之类）。按计划的原文，`M8` 要的是**文件**。

两种分母都算一遍：

| 分母 | C: 冷 | D: 冷 | 合计 39.030 s | 对 200 万目标 |
|---|---|---|---|---|
| **记录**/分钟（含目录与元数据） | 7,565,897 | 13,329,549 | 10,133,476 | 5.07× |
| **文件**/分钟（严格） | 5,699,368 | 11,890,912 | 8,457,563 | **4.23×** |

**但上表有一个问题：「冷」这个字样从第二轮起就不成立。** 同一台机器、同一条代码、同一份数据，D: 在相隔 29.5 分钟的两轮之间从 **38.940 s** 掉到 **17.387 s**（快 2.24 倍）——MFT 留在系统缓存里没被换出去。探针自己把第一轮的标签写成「冷，**可能**真读盘」，这个措辞是对的。

所以**可辩护的数字取「每卷历次实测里最慢的那一次」**：

| 卷 | 历次最慢（第 1 轮） | 文件数 | 文件/分钟 |
|---|---|---|---|
| C: | 23.047 s | 2,053,815 | 5,346,852 |
| D: | 38.940 s | 3,445,784 | 5,309,374 |
| **合计** | **61.987 s** | **5,499,599** | **5,323,309** |

**结论：`M8` 达成。** 最保守的读法（文件分母 + 每卷历次最慢 + 两卷加总）是目标的 **2.66 倍**；同一次运行内的读法是 **4.23 倍**。**两种算法方向一致，结论不依赖取哪一种。**

> **本机首次装机把两卷各过一遍的最坏情形是 62 秒。** 相对首轮嵌入预估的 754 小时，枚举这一环**不在关键路径上**——这个事实对 `D11` 的分量见下一节。

## 2.2 D11 那句「枚举快约 40 倍」站不住，但 D11 本身仍然成立

计划 §4.8 写着（§3.2 同）：

> 若改为 `HighestAvailable`，D11 的 MFT + USN Journal 后端可用：**枚举快约 40 倍**……

C: 同卷、同一提交的对照：

| | 条目/记录数 | 耗时 | 忙率 |
|---|---|---|---|
| MFT 冷 | 2,729,145 条记录 | 21.643 s | 7,565,897 记录/分钟 |
| MFT 暖 | 2,729,145 条记录 | 8.747 s | 18,720,556 记录/分钟 |
| scandir | 3,470,303 个目录项 | 122.946 s | 1,693,574 目录项/分钟 |

**实测倍数：冷 5.68×、暖 14.06×**，不是 40×。

**错在哪**：那个 40× 由两个假设相除得到——scandir「5 万文件/分钟」、MFT「200 万文件/分钟」。实测：

- scandir **169 万条目/分钟** → 计划**低估 33.9 倍**
- MFT **757 万记录/分钟** → 计划低估 3.8 倍

**两边都估低了，但 scandir 被低估得狠得多，于是比值从 40 掉到 5.7。** 计划里那个「5 万文件/分钟」多半是照搬了别的工具在别的机器上的观感，**本机的 `os.scandir` 没那么慢**。

**这不是把 D11 推翻，是把它的理由换掉**：

1. **5.7× 仍然值得做**，尤其配合 §2.1 那句"枚举不在关键路径上"——真正的收益不在首轮全量，而在增量。
2. **D11 真正的主理由从来是 USN，不是枚举倍数**：增量场景下 USN 只返回**变化**，代价从"每次走遍全盘"降到"读一条日志"。**这一条与 5.7× 还是 40× 毫无关系**，而它才是 `D11` 不可替代的部分。
3. **但计划里那句数字必须改**，否则以后照它做取舍（比如"为了 40× 值得默认提权"）就会错。

> **要不要因此打开计划任务的管理员权限？** 计划 §4.8 的两条取舍 **本次不改**。§2.1 显示枚举只值 62 秒，而 §2.4 显示 USN 在本机有一半的盘不可用——**"为了 40× 而提权"这个理由消失了，得重找**。这件事留给 P2 落地时按真实需求决定，不在此处顺手改。

## 2.3 两种后端数出来的「文件数」不是同一个东西

C: 同一块盘：

| | 文件 | 目录 |
|---|---|---|
| MFT（记录） | 2,055,857 | 673,288 |
| scandir（目录项） | 2,814,788 | 655,515 |
| 差 | **+758,931** | **−17,773** |

**这不是误差，是口径不同**：

- **MFT 数的是记录**——一个文件一条，无论它有几个名字
- **scandir 数的是目录项**——一个名字一条

NTFS 支持硬链接，一个文件可以有多个名字。用 `fsutil hardlink list` 在 `C:\Windows\System32` 抽查：

```text
kernel32.dll       → 2 个名字
notepad.exe        → 3 个名字
win32kbase.sys     → 2 个名字
```

**目录方向相反**（scandir 反而少 17,773），与「跳过 422 个 reparse point 后其子树未被下潜」一致：不下潜就数不到子树里的目录，而硬链接只影响文件那一侧。

> 那个跳过是 `80760d3` 修的。修之前 `scandir_count` 会跟随 junction 下潜，同一棵树被反复数——在 `%LOCALAPPDATA%` 这一类含指回自身 junction 的树上实测：**不跳 61.989 s 对跳 27.784 s（2.23×），文件虚高 12,101**。
>
> ⚠ **这两个数的出处要交代清楚**：它们是修 bug **之前**的一次**临时测量**，**没有归档成日志**——当时的原始输出没落盘，数字只记在提交 `80760d3` 的消息里。**本报告的分析不依赖它们**（`F0-04` 的结论都建立在 §1 那三份已归档的输出上），它们在这里只是解释"为什么要修"以及"全盘 scandir 基线为什么必须跳过 reparse point"。**要当数字引用，先重跑一次并归档。**

**没有做的那件事**：**没有逐条把 758,931 归因给硬链接。** 机制确认了、方向对、量级也合理（WinSxS 里大量文件 2–3 个名字），但**没有配平**。要配平得按 FRN 折叠后逐条比对，那是 `F2-02` 的活。此处如实记为「机制已确认、配平未做」。

**对计划的直接影响**（这条要回改计划）：`F2-02` 约定的是「含与 scandir 的**逐条一致性**」。按现在的口径，**两者在计数上不可能一致**。核对必须定义成**按 FRN 折叠硬链接后的集合相等**，不是数字相等——否则 `F2-02` 会拿着一个永远满足不了的判据，然后要么被静默放宽、要么被当成实现有 bug。

## 2.4 USN Journal：C: 有、D: 没有——而 D: 正是放项目与文档的那块盘

| 卷 | USN Journal |
|---|---|
| C: | **有**。`NextUsn=36,031,993,080`、`FirstUsn=35,995,516,928`、最大 32.00 MiB |
| D: | **没有**。`WinError 1179 ERROR_JOURNAL_NOT_ACTIVE` |

**这条的分量在于 D: 是数据盘。** 也就是说 `F6-01`（USN 增量）打算建立的"秒级增量"**在 D: 上开箱即用是不成立的**，除非先 `fsutil usn createjournal m=<MB> a=<MB> D:` 建一个。**探针刻意不替你建**——那会改卷上的元数据，属于用户该拍板的事。

**顺带量到一个数**：两次提权跑相隔 **29.5 分钟**（17:45:24 → 18:14:52），C: 的 `NextUsn` 增长 **21,485,768 字节 = 20.49 MiB**，折合 **0.70 MiB/分钟**；按最大 32 MiB 算，**写满一圈约 46 分钟**。

- ⚠ **这不是干净的空闲基线**：那 29.5 分钟里本机正跑着全盘 scandir 遍历和我自己的一堆进程，写入量被抬高了。**当作量级参考，不要当作精确速率。**
- 但它对 `R17` 有意义。`R17` 的原话是「USN Journal 被重置或回绕」，严重度记的是「中/中」，应对是「发现越界即回退全量扫描」。**实测这个圈转得相当快**：即便把上面那个速率再打个折，C: 上的回退也不会是罕见事件。**`R17` 的应对措辞要按这个观察重估**——不是"要不要回退"，而是"回退多频繁才算正常"。

## 2.5 `GetDriveType` 不足以判定「本地盘」（R15 / D11 的输入）

探针按 `GetDriveTypeW == DRIVE_FIXED(3)` **且** 文件系统为 NTFS 来决定要不要走 MFT。本机 **E: 两项都满足**，但用户 2026-10-14 明确指示 **E: 不是本地盘**（同一次指示：以后一切文件操作只碰 `C:` 和 `D:`）。

**所以 `D11` 的 `backend="auto"` 与 `R14` 的 `--prune` 都不能拿 `GetDriveType` 当"这卷是本地、且会一直在"的判据。** USB 硬盘盒、VHD、iSCSI 目标**都报 `DRIVE_FIXED`**。猜错的代价是不对称的：`--prune` 按"卷不可达就跳过"是安全的，但**把一个会掉线的卷当成固定盘去建全量索引**，会得到一份永远追不平、且随时可能误判为"文件都删了"的索引。

P2 落地时要另找证据（或让用户显式配置哪个卷算本地）。**这条只记现象，不给方案。**

## 2.6 探针自己踩的四个坑，都是「不报错、只给错结论」

记下来是因为每一个都会让报告说谎，而且**前三个都不表现为崩溃**：

1. **`GetProcessMemoryInfo` 在 `psapi.dll`，不在 `kernel32`。** 直接 traceback。与 `bench_embed.py` 对齐后修。
2. **`--scandir` 不给卷名时会去遍历"全部 MFT 成功的卷"**，包括 1.37 TB 的 D:。改成 `nargs="?"` + 显式门控，默认只做 `ALL` 里点名的那些。
3. **`Tee` 不 flush，日志在进程退出前一直是 0 字节。** `-u` 只作用于**被替换掉的那个原始 `stdout`**；一旦把 `sys.stdout` 换成自己的 `Tee`，`-u` 就管不着它了。修法是在 `Tee.write` 里自己 `flush()`、日志文件 `buffering=1`。**这个坑的坏处正是"看起来成功了，但日志是空的"**——探针跑了 62 秒、终端上有输出、文件 0 字节。
4. **scandir 跟随 reparse point 下潜**，实测 2.23× 时间、12,101 个虚高条目（见 §2.3）。**单独一个提交 `80760d3`**，因为它同时是 P2 的输入：`F2-01`（scandir 后端）与 `R4` 必须处理 reparse point，否则全盘扫描既慢又数不准。

## 2.7 可复现性：两轮的计数几乎一致

相隔 29.5 分钟的两轮提权跑：

| 卷 | 记录 | 目录 |
|---|---|---|
| C: | 2,727,103 → 2,729,145（**+2,042**） | 673,288 → 673,288（**0**） |
| D: | 3,862,675 → 3,862,681（**+6**） | 416,891 → 416,893（**+2**） |

**增量全是正数，量级与那 29.5 分钟里的实际写入相符**（C: 的 USN 同期长了 20.49 MiB）。**两轮之间没有任何删除或重命名导致计数下降。**

这是个**弱但真实**的"枚举结果稳定"信号：它说明同一台机器上重复枚举的确定性是好的。**它不构成 `F2-02` 的一致性验证**——那要在同一时刻对同一卷跑两种后端并逐条比对，本次没做。

## 2.8 一条推理，明标记为推理

样本里 8 条记录的 `TimeStamp` 打印出来**全是 `—`（即 0）**，而同一个结构里的 `USN` 字段是有值的（如 `USN=35819643304`、`USN=34137324376`）。

**我的推断是**：`FSCTL_ENUM_USN_DATA` 返回的记录本来就**不填**时间戳（它是"枚举"不是"追变更"），所以 0 是正常的。

**支持这个推断的是**：同一个结构里的 `FileNameLength` / `FileNameOffset` 解出来完全正确（文件名一个个读得通、目录与文件的分类也合理），说明 60 字节的 `USN_RECORD_V2` 布局没有错位——**若布局错位，文件名会先乱掉**。

**但这是推理，不是独立验证。** 要证伪只需找一个已知修改时间的文件、看它返回的 `TimeStamp` 是否仍为 0。**本次没做。** 之所以记在这里：`F6-01`（USN 增量）要靠时间戳判断"这条变更是什么时候发生的"，**如果 ENUM 与 QueryUSNJournal 对时间戳的填充规则不同，那就是个会静默给出错误时间的坑**。

# 3. 遗留

1. **scandir 基线只在 C: 上做了，D: 没做。** 所以 §2.2 那个 5.68× **只在 C: 上成立**，不能直接推广到 D:（D: 有 386 万条、1.37 TB，scandir 预估要十几分钟）。要么补测，要么在文档里把结论**限定为 C: 的结论**。
2. **"冷"不可复现。** 真正的冷启动要重启机器或清文件系统缓存，本次做不到。§2.1 用"取历次最慢"回避了这个问题，但**那不是真冷，是"最不容易是热的"**。
3. **758,931 的硬链接配平未做**（见 §2.3）。机制确认、量级合理、**没有逐条证明**。
4. **`TimeStamp` 恒为 0 只有推断没有验证**（见 §2.8）。
5. **D: 上没有 USN Journal**，`F6-01` 在 D: 上的可行性取决于用户是否愿意建（见 §2.4）。这是**要用户拍板**的事，不是实现细节。
6. **`--volumes` 默认值是"所有已挂载卷"**，与"只碰 C: 和 D:"的指示相冲突。本次靠显式传参绕开，**探针没有改默认值**——因为它是诊断工具、默认穷举本身合理，但如果将来有脚本复用它，**这是个等着踩的坑**。
