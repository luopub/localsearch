> **本文件与 [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md) 的分工**
>
> 计划文档记录**打算做什么**；本文件记录**实际发生了什么**。

>

## 记录约定

| 何时写 | 写什么 |
|---|---|
| 每完成一个阶段 | 更新 §1 状态总览、填写该阶段小节、追加 §6 变更日志 |
| 每次测量 | 立刻填进 §3 实测数字表，**不要让数字留在终端里** |
| **每完成一个功能点** | 写实现 + 写测试 → **提交** → 在这个提交上跑测试 → 通过就推送 → 把 commit id 回填三处。**这个顺序不能颠倒**，理由见计划 §10.6。**没有测试的功能点不算完成** |
| 每次跑测试（含回归） | 记进对应阶段的「测试记录」；测试文件或被测模块被改过的功能点，§5.2 状态回退为「待复测」 |
| **每次推送之后** | **立刻**把 commit id 写进三处：该条测试记录的「代码版本」栏、§5.2 的「最近一次记录」栏、§6 该条改动末尾。**没记 id 的改动等于没留追溯线索** |
| 遇到意外 | 写进该阶段的「与计划的偏差」。**只记成功等于没记** |
| 决定变更 | 追加 §6，并回改计划文档的对应条目 |

**只记三类信息**：实测数字、与预期的偏差、无法立刻解决的问题。流水账没有价值——「今天写了 scanner.py」这种话不要写。

> **测试记录是这之外的第四类，不算流水账。** 理由：每条测试记录都带实测计数与代码版本，它直接改变"这个功能点还算不算受保护"的判断——符合本文件唯一的取舍标准（能不能改变将来的某个决定）。但「跑了测试，没问题」这种没有计数的写法就是流水账，见计划 §10.4 的反例。

### 时间戳（硬性要求，见计划 §10）

**每一条「事件」前面必须有一个精确到秒的时间戳**，格式固定为 `YYYY-MM-DD HH:MM:SS`（24 小时制，本机本地时间 UTC+8），写在条目最前：

```
- 2026-10-14 03:12:03  新增 scripts/windows/ 计划任务定义
```

- **精确到秒，不要只写日期。** 这个项目一天之内会发生多次判断反转，只写到日期就丢失了先后顺序，而"这条标准是在测出吞吐之后放宽的，还是之前"正是复盘要看的东西。
- **时间必须来自机器**：记录当时发生的事取系统当前时间；补记已发生的事取文件时间（`stat`）或 `git log --format=%ai`；确实无从考证写 `（时间未记录）`并说明原因，**不要猜**。
- 落点：§3 有独立的「测量时间」列；§4 每条记录带时间前缀；§5 证据栏带取证时间；§6 每条以时间开头并按时间**倒序**。

## 4. 各阶段记录

每阶段固定五栏。**「与计划的偏差」和「遗留」两栏不允许留空**——没有偏差就写"无"，没有遗留也要明确写"无"，逼自己确认过。

每条填进去的记录（尤其「测试记录」）前面带 `YYYY-MM-DD HH:MM:SS` 时间戳，见 §记录约定。

**「测试记录」栏按功能点逐条列，一行一条**，六个字段缺一不可（时间戳 / 功能点 ID / 命令 / 结果 / 代码版本 / 关联验收项），格式与理由见计划 §10.4：

```
- 2026-10-14 14:02:11  F2-03  `uv run pytest tests/unit/test_filters.py -q`  → 18 passed  ·  8c319cc 干净  ·  A8
```

**失败的测试同样要写进这一栏**，并且跟一句原因或后续动作——只记成功等于没记。同一功能点重跑之后，**追加**新的一条，不要覆盖旧的那条（新旧两条正是判断"这次改动有没有弄坏东西"的依据）。

**「代码版本」栏怎么填**——按计划 §10.6 的固定顺序，测试跑在**代码提交之后、推送之前**，所以正常情况下这里就是一个干净的 commit id。三种情况：

| 情况 | 写法 | 含义 |
|---|---|---|
| 正常 | `c6974fe` | 这就是被测代码，工作区干净，别人 clone 到同样结果 |
| 边写边跑、代码还没提交 | `工作区脏（基于 bba9a2d）` | 这一版**没有提交过**，随时可能变。这是探索期的临时写法，**不能作为 `已通过` 的依据** |
| 推上去之后才发现测试不过 | 新开一条记录写失败的输出 | 旧记录**不要改**，另起新提交修，注明"前一个提交的绿灯是错的" |

**这条记录最终必须落到一个 commit id 上**，否则它只是一次无法复现的观察。

**本文件自己的改动要单独提交，不要混进代码提交里。** 因为 commit id 在提交之前不存在——把"本次的 id"写进它自己那个提交，写完 id 就变了。所以固定成：**先提交代码（拿到 id）→ 再记录（引用该 id）→ 记录另起一个文档提交**。详见计划 §10.6。

### 5.2 功能点 → 自动化测试总账

**每个功能点必须有一条自动化测试，并且测试跑过之后在 §4 对应阶段的「测试记录」里留下一条带代码版本的记录。** 规则、字段、例外见计划 §10.4。

「最近一次记录」栏写 `YYYY-MM-DD HH:MM:SS  <commit id>`（例：`2026-10-14 14:02:11  a1b2c3d`）。**没有 commit id 的功能点，状态不能是 `已通过`**——`已通过` 的含义是"在这个 commit 上通过"，只写时间戳说不清是哪一版。

状态取值：

| 状态 | 含义 |
|---|---|
| `未开始` | 代码还没写 |
| `已通过` | 有记录，且记录里的代码版本之后**没有改过被测文件**（判定口径见下方引用块） |
| `失败` | 最近一次记录是失败，必须跟一条原因 |
| `待复测` | 曾经通过，但测试文件或被测模块之后被改过——**绿色不会自动续期** |

> **`已通过` 的判定口径**——2026-10-14 第一次真的有功能点转绿（`F0-05` / `F0-06`）时被迫定下来的，此前 49 条无一通过，**没有先例可依**。
>
> 本条原先写的是"记录里的代码版本就是**当前** HEAD"。这句话按字面执行不了：按项目固定的提交顺序（计划 §10.6），记录必须写在**它自己那个文档提交之前**、引用一个**已经存在**的代码提交，于是文档提交一发生，HEAD 就不再等于记录里的 id。所以真正的判据是：
>
> ```bash
> git diff --stat <记录里的 id>..HEAD      # 只应出现 docs/ 下的改动
> ```
>
> **只要被测文件被动过就回退成 `待复测`；只动文档不算。** 这与「绿灯不自动续期」是同一条规则的两面。
>
> **2026-10-14 `F0-04` 转绿时给这条判据补了一个口径**：`git diff --stat 5c488fe..HEAD` 里出现了 `tools/probe_mft.py`（+822 行），而它**不是 `F0-01`/`F0-02`/`F0-03` 的被测文件**——那三条的被测文件是 `tools/bench_embed.py`，自 `5c488fe` 起**一行都没动**（同一次核对里 `git diff --stat 21c07d3..HEAD -- tools/probe_deps.py` 也是空的，故 `F0-05`/`F0-06` 的绿灯同样成立）。
>
> 所以上面那句"只应出现 docs/ 下的改动"要按**意图**读，而不是按字面：**判据问的是"这个改动能不能改变该功能点的结论"**。一个与该功能点无关的**新增**文件不能，所以绿灯保留。同理要留意的是**会实质影响结论的配置改动**（依赖集、配置语义）——这次窗口里 `pyproject.toml` 确实动过（补了第 19 个包 `torchvision`），但它与"FAISS/hnswlib 可用性""FTS5 + jieba 可用性"两条结论无关，故不影响。**这一层判断标准上文没有写，是这次补的。**

  - 另一条独立的坑：`rem` 行会把整行吞掉，`&` `|` `<` `>` 都不会被解释。实测 `rem before & echo SPLIT` 不打印 `SPLIT`，`rem ... > probeout.txt` 也不产生文件。故注释里可以放心写这些字符
